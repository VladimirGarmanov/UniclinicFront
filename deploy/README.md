# Установка uniclinic.pro на 194.156.116.81

Канонический адрес: **https://uniclinic.pro**. Сервер: **root@194.156.116.81**.
`www` и HTTP перенаправляются на основной HTTPS-адрес. Формы обращаются к `/api`
на том же домене. Backend слушает только `127.0.0.1:8000`; IP сервера в браузерный код не добавляется.

Скрипт `server.py` рассчитан на **Ubuntu 24.04 или 26.04**, systemd и архитектуру x86_64/arm64.
На другой ОС он останавливается до изменений. ОС и конфигурация указанного сервера
удалённо не проверялись. Это инструкция для самостоятельного запуска: публикация ещё не выполнена.

## 1. Отправить изменения в GitHub с Mac

В проекте два отдельных репозитория. Выполнить для каждого:

```bash
cd /Users/vladimir/PycharmProjects/UNICLINIC/UniclinicFront
git status --short
git add -A
git diff --cached --stat
git commit -m "Prepare static frontend and production deployment"
git push origin main

cd /Users/vladimir/PycharmProjects/UNICLINIC/UniclinicBack
git status --short
git add -A
git diff --cached --stat
git commit -m "Protect patient submissions and prepare production API"
git push origin main
```

Перед `commit` просмотреть список подготовленных файлов. `build`, `node_modules`,
`.venv`, `.env` и локальная база исключены из новых коммитов через `.gitignore`.
Старая `.env` backend уже была в истории Git: её удаление из текущей версии не очищает
историю. Старые реальные пароли нужно заменить. Исходные CMS-снимки frontend также
содержат контактные поля, которые сборка исключает из сайта: **репозитории с этими
исходниками должны оставаться приватными**. Не публиковать raw JSON или исходную папку
`public/upload` как отдельный сайт. Для установки используются только коммиты, а не незакоммиченные файлы.

## 2. Подготовить домен

В DNS:

| Запись | Значение |
| --- | --- |
| A для `uniclinic.pro` (`@`) | `194.156.116.81` |
| CNAME для `www` | `uniclinic.pro` |

Если есть AAAA, она должна вести на рабочий IPv6 этого же сервера; устаревшую AAAA
нужно убрать. На время первичной установки записи должны вести прямо на сервер.
Разрешить входящие TCP 80/443 в панели хостинга и существующем firewall; сохранить
доступ SSH. Порт 8000 наружу не открывать. Установщик не меняет DNS и firewall.

Если домен сейчас обслуживает старый сервер, переключение DNS планировать на окно
переноса: до завершения установки новый сервер отвечает 503, кроме проверки сертификата.
Сборку можно подготовить командой `build` до переключения DNS (см. ниже).

## 3. Клонировать и установить окружение

Подключение с Mac:

```bash
ssh root@194.156.116.81
```

Далее на сервере:

```bash
cat /etc/os-release
apt-get update
apt-get install -y git python3
mkdir -p /opt/uniclinic
cd /opt/uniclinic
git clone https://github.com/VladimirGarmanov/UniclinicFront.git
git clone https://github.com/VladimirGarmanov/UniclinicBack.git
cd /opt/uniclinic/UniclinicFront
python3 deploy/server.py setup
```

Для приватных репозиториев GitHub запросит учётные данные; вместо пароля аккаунта
используется токен с доступом на чтение этих репозиториев. Не вставлять токен в URL
или в команды. Альтернатива — заранее настроенный SSH-доступ к обоим репозиториям.

`setup` устанавливает nginx, Certbot, Python venv и инструменты сборки, скачивает
Node **24.21.0** с проверкой SHA-256 и создаёт двух служебных пользователей. npm и pip
выполняются от `uniclinic-build`, API — от `uniclinic`. Системный Node не заменяется.
Пароль администратора генерируется в `/etc/uniclinic/backend.env` с правами 600.
Уже существующий файл настроек сохраняется.

При обнаружении чужого nginx-конфига для uniclinic.pro или одноимённой службы скрипт
останавливается и показывает конфликт. Сначала сохранить и разобрать старую конфигурацию;
не удалять её вслепую. Остальные сайты скрипт не отключает.

## 4. Выбрать базу обращений

**Выполнить только один из следующих вариантов.** Статические статьи, врачи и новости
уже находятся во frontend; здесь речь о частных обращениях и отзывах в SQLite.

Если запускаем новую пустую базу:

```bash
python3 deploy/server.py database --empty
```

Если сохраняем обращения со старого сервера: получить согласованную резервную копию SQLite
(через SQLite backup API, а не копирование работающего файла без WAL), безопасно перенести
её в `/root/uniclinic-previous.sqlite`, затем:

```bash
python3 deploy/server.py database --from-file /root/uniclinic-previous.sqlite
```

Существующую рабочую базу команда никогда не перезаписывает. Импорт проверяет целостность.
При первом запуске API добавляет новые поля. Старые обращения остаются приватными до
явного одобрения публикации через админку. Импорт и миграцию реальной старой базы нужно
проверить на её копии; локальные проверки использовали только искусственные данные.

## 5. Собрать и запустить

```bash
python3 deploy/server.py deploy
```

Команда собирает frontend, устанавливает backend из lock-файла, получает сертификат
для обоих доменов, сохраняет копию базы, переключает релиз и запускает службу.
Certbot при первом запуске запросит email и принятие условий. Нужны рабочие DNS и порт 80.
Короткая проверка сборки и четыре HTTPS-запроса проверяют главную, API, sitemap и 404;
большой набор тестов не запускается. Сборка изображений при первом запуске может занять
заметное время. Скрипт требует хотя бы 4 GiB свободного диска; это минимальный порог,
а не расчёт места для неограниченного числа релизов.

После успешного завершения:

- Сайт: **https://uniclinic.pro**.
- Админка: **https://uniclinic.pro/questions/admin**.
- Пароль: значение `ADMIN_PASSWORD` в `/etc/uniclinic/backend.env` (читать локально на сервере).
- Обращения сохраняются в базе. Email-уведомления выключены, пока не заполнены SMTP-настройки.

Настройки можно открыть командой `nano /etc/uniclinic/backend.env`. После изменения:

```bash
systemctl restart uniclinic-api
python3 deploy/server.py status
```

Для почты заполнить `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
`SMTP_USE_SSL`, `MAIL_FROM`, `MAIL_TO`. Не отправлять этот файл в GitHub.
`SITE_ORIGIN`, `CORS_ORIGINS` и `COOKIE_SECURE` уже настроены для https://uniclinic.pro.

Если сертификат пока получить нельзя, подготовить сборку отдельно:

```bash
python3 deploy/server.py build
```

Команда напечатает `Release prepared: /srv/uniclinic/releases/...`. После настройки DNS
выполнить `python3 deploy/server.py certificate`, затем `python3 deploy/server.py activate --release`
с полным путём напечатанного релиза. Это позволяет не повторять сборку.

## Обновления и откат

После следующих коммитов и push обоих репозиториев:

```bash
cd /opt/uniclinic/UniclinicFront
python3 deploy/server.py update
```

Команда выполняет `git pull --ff-only origin main` в обоих репозиториях, собирает новый
релиз и активирует его. При локальных изменениях или другой ветке она останавливается,
не делает reset/clean. Во время сборки работает старый сайт; переключение включает
короткий перезапуск API. При ошибке активации восстанавливаются предыдущая ссылка
релиза и конфиги; восстановление после аварии самого сервера может потребовать ручных действий.

Откат на предыдущий успешно установленный релиз:

```bash
python3 deploy/server.py rollback
```

Откатываются код и конфиги. **База не откатывается**, чтобы не потерять новые обращения.
Текущие миграции добавляют поля; при будущих несовместимых миграциях потребуется отдельный
план восстановления. После первого запуска предыдущего релиза ещё нет.

## Диагностика, сертификат и резервные копии

```bash
cd /opt/uniclinic/UniclinicFront
python3 deploy/server.py status
journalctl -u uniclinic-api -n 60 --no-pager
nginx -t
systemctl status certbot.timer --no-pager
python3 deploy/server.py backup
```

Резервная копия SQLite создаётся перед каждым переключением и вручную командой `backup`.
Это локальные копии на том же сервере, не полноценная внешняя система резервирования.
Автоматическое удаление релизов, кеша и копий отключено; место нужно контролировать.
Нужны отдельное расписание копирования вне сервера, срок хранения и проверка восстановления.
Certbot timer продлевает сертификат; deploy-hook проверяет nginx и перезагружает его.

| Путь | Назначение |
| --- | --- |
| `/opt/uniclinic/UniclinicFront`, `/opt/uniclinic/UniclinicBack` | Клоны Git |
| `/opt/uniclinic/toolchain` | Отдельный Node для сборки |
| `/srv/uniclinic/releases` | Готовые релизы с собственным Python venv |
| `/srv/uniclinic/current`, `/srv/uniclinic/previous` | Активный и предыдущий релиз |
| `/srv/uniclinic/shared/assets`, `/srv/uniclinic/shared/media` | Ресурсы с хешами, включая старые для открытых вкладок |
| `/var/lib/uniclinic/questions.db` | Приватная база, доступна только API |
| `/etc/uniclinic/backend.env` | Настройки и секреты, только root |
| `/var/backups/uniclinic` | Копии базы и конфигурации, только root |
| `/var/cache/uniclinic` | Рабочие каталоги и кеш сборщика |

## Что отдельно от установки

Метрика и Вебмастер отложены по решению владельца; внешние счётчики не подключаются.
SMTP, внешние алерты, DKIM/DMARC и размещённая staging-среда требуют отдельной настройки.
Перед публикацией клиника подтверждает контакты, тексты согласия и право публикации
исторических медицинских обращений. Отсутствующие биографии/документы не придуманы.

Локальную staging-сборку можно сделать через
`STAGING=true SITE_ORIGIN=https://staging.uniclinic.pro npm run build` и `npm run preview`.
Для размещения staging нужны отдельные БД/секреты и ограничение доступа; основной
установщик намеренно собирает production для uniclinic.pro.

Источники для установки: [официальные контрольные суммы Node 24.21.0](https://nodejs.org/dist/v24.21.0/SHASUMS256.txt)
и [Certbot webroot](https://eff-certbot.readthedocs.io/en/stable/using.html#webroot).
